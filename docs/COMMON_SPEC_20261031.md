```json
    "game_slug": "tomatoku_competition_v1",
    "title": "トマトオク",
    "game_url": "https://chameleonjp-lab.github.io/tomatooku/",
    "is_active": true,
    "release_date": "2026-07-19",
    "score_order": "asc",
    "score_scale": 100,
    "score_decimals": 2,
    "score_unit": "秒",
    "top_ranking_type": "best",
    "submission_mode": "verified"

```

サーバーの既存参加者は表示名で識別される。このままでは同名の別人を区別できず、改名で同じ参加者を保つことも保証できない。今回データを削除/再構築したり、全記録を新しい参加者へ割り当て直したりしない。別途、安定したparticipant IDと旧記録の所有確認/移行方式が必要。上位30名の厳密な「本人単位」の達成はこの制約が残る。API集計と詳細ランキングの既存名前単位集計は一致させる。表示名や上位一覧から圏外順位/全人数を推測しない。

## 適用順・公開後確認・切戻し

**設定が必要**: Settings → Pages → Build and deployment → Source を `GitHub Actions` に変更する。現在は `main` の branch配信（legacy）。ユーザーのマージ前には変更しない。マージ後のworkflow検証成功と同じSHAを確認して設定を切替え、workflow_dispatchでmainを再実行。旧branch配信との二重公開を防ぐ。設定変更をこの作業で実施したとは報告しない。

1. PR差分とCIを確認し、ユーザーが `main` へマージする。直接push/自動マージはしない。
2. マージコミットの検証/ビルド/公開が成功したことと、公開URLの共有ラベル・ランキング詳細導線・今回の変更を確認する。PR段階の成功を本番公開済みとは扱わない。
3. iPhoneで名前空欄→開始→結果→ランキング、名前変更後の次プレイ、Xをキャンセルして復帰、音オフ/0→再読み込み、縦横とキーボード表示を短く確認する。実データへの多数の試験登録は避ける。
4. 問題があればこのPRをrevertする新PRを作成し通常の検証/マージで戻す。DB行/設定/自己ベストを消さない。Pages設定を変更した場合は元の `legacy` / `main` 設定と既存公開artifactを記録して戻す。元の実行が新しい公開を後から上書きしないよう、古い実行を再実行しない。
